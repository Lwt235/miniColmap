# 初始化耗时上升排查

日期：2026-10-17。只新增独立诊断脚本和报告，未修改几何、建图或优化算法。

**后续修正：** 本报告约40秒的重放发生在沙箱内，不能直接与宿主上的Web工作进程对比。后续已在同一宿主重现103.5秒，并通过仅改变进程Windows QoS降至31.1秒，算法和初始地图完全一致；详情及实际Web重建验收见 [Web性能修复报告](2026-10-17-web-performance-fix.md)。下文保留原始测量及当时结论的证据范围。

## 结论

**没有复现出自适应 RANSAC 导致初始化计算量大幅上升。** 在同一 Python 进程里交替重放旧、新匹配结果，新结果初始化并不比旧结果明显更慢。此前 15.9 / 144.7 秒的异常尚不能归因到某一个具体环境因素；历史日志没有进程 CPU 时间、系统负载或调试状态，不能凭现有信息认定是后台程序、调试器或电源模式。

**已确认的初始化瓶颈是：每个候选图对都先做两视图精化，最后才选初始对。** 新 47 图有 218 个候选，其中 217 个进行精化，耗时约占初始化的 77%–78%。关闭 `bundle_adjustment.enabled` 仅跳过后续全局 BA，不会关闭初始化中的 `refine_two_view`。

## 对照方法

从各运行的 `features/*.npz`、`matches/*.npz`、`pairs.json` 恢复完全相同的关键点、F 和内点，重新建立 tracks，只执行当前 `initialize_map`。不重跑 SIFT 或 RANSAC，不读取真值，不修改原运行文件。

每组旧、新输入在同一进程中分别执行两次，第二轮调换顺序。测量包含轻量函数计时包装；细分时间为包含子调用的墙钟时间，嵌套项不能相加。表内为当前机器的诊断结果，不是稳定的跨机器性能承诺。

| 输入 | 原日志初始化 / 秒 | 本次 M1 重放两次 / 秒 |
|---|---:|---:|
| 旧固定预算 8 图 | 4.594 | 6.429 / 5.254 |
| 新自适应 8 图 | 15.895 | 4.751 / 5.601 |
| 旧固定预算 47 图 | 38.688 | 39.663 / 43.253 |
| 新自适应 47 图 | 144.694 | 38.557 / 41.378 |

旧日志计时含初始化后的校验、诊断落盘和 UI 快照；重放计时只覆盖 M1，所以额外进行了完整 worker 验证，见下文。两次重放足以检查是否重现几倍的差距，不足以测定几个百分点的性能差别。

**全部 14 次重放（包括单线程、cProfile 和最终脚本冒烟检查）生成的初始化地图哈希，都与各自原运行的 `snapshot-0001.json` 一致。** 初始相机、点坐标、颜色、观测和关键点保持原结果，精化的 nfev 合计也复现。

## 时间实际花在哪里

以下取新 47 图第二次重放，总计 41.378 秒。

| 非嵌套主项 | 秒 | 占比 |
|---|---:|---:|
| 两视图精化 `refine_two_view` | 32.199 | 77.8% |
| 相对位姿恢复 `recover_relative_pose`，含四组解的三角化 | 6.884 | 16.6% |
| M1 中额外一次三角化 | 1.679 | 4.1% |
| 其余：索引、筛选、记录和验证等 | 0.616 | 1.5% |

精化内部主要包含稀疏线性子问题、数值 Jacobian 和稀疏结构构造。LSMR 子问题累计约 15.937 秒，**已包含在上面的 32.199 秒内**。217 次精化合计优化了 46,008 个图对点实例，同一个场景点可能在不同候选中重复出现。

进一步比较工作量：

| 指标 | 旧 47 图 | 新 47 图 |
|---|---:|---:|
| 候选图对 | 219 | 218 |
| 两视图精化次数 | 218 | 217 |
| 精化 nfev 合计 | 3507 | 3213 |
| LSMR 调用 | 2790 | 2569 |
| LSMR 内层迭代合计 | 220879 | 203092 |

这次不仅 nfev 更少，线性子问题的调用和内层迭代也更少，因此“提前停止让初始化做了更多优化”不符合这批输入的实测。

## 排查的其他因素

1. **内参矩阵求解**：新 47 图 `np.linalg.solve` 累计约 0.025–0.029 秒，1087 次调用；不是当前瓶颈。
2. **BLAS 线程**：当前 NumPy/SciPy 的 OpenBLAS 各默认 20 线程。独立进程限定为 1 线程后，新 8 图约 4.452 / 4.417 秒；默认线程为 4.751 / 5.601 秒。未出现足以解释原异常的数量级变化。这只验证了当前 8 图线程对照，不追溯当时的线程状态，也没有改服务或系统环境变量。
3. **einx 首次编译/缓存**：旧 47 图作为冷启动输入时，所有 `einx.dot` 累计约 4.026 秒；新 47 图随后约 1.013 秒，第二轮约 0.174 秒。这是可见的小开销，但不足以解释多出的约 100 秒。它嵌套在多个主项内，不单独相加。
4. **界面连接层**：用新 8 图的同一配置，直接调用真实 `ui.worker.main`，重新执行完整流水线，保留它的事件、元数据和快照写入。输出写入独立 `.cache` 目录，不占用工作台任务。初始化阶段 **3.586 秒**，其中 M1 **3.504 秒**，其余共 **0.082 秒**；初始化快照写入约 **0.021 秒**。完整流水线 10.156 秒，最终 `model.json` 与原新 8 图逐项完全相同。此验证包含 worker 写入，不包含浏览器 HTTP 请求、渲染及其可能造成的 CPU 争用。
5. **调试/剖析开销**：单独启用 cProfile 的新 8 图重放为 8.628 秒，明显慢于轻量计时。该数字只用于识别函数成本，不能与普通运行直接当作速度对比；也不能据此证明旧异常由调试器造成。

完整 worker 重跑中，SIFT 仍约 0.798 秒，接近旧新运行的 0.833 秒；而 Python 为主的 RANSAC、tracks、初始化、导出都明显快于那次异常运行。因此现有证据更支持**当次执行环境或附加开销造成整体运行速度变化**，而非自适应公式增加了初始化工作量。具体环境因素尚未确定。

## 后续处理

暂不改动自适应 RANSAC，也不放宽几何筛选阈值。若要优化正常情况下约 40 秒的初始化，优先考虑“廉价检查后再对少量候选做精化”，因为目前绝大多数精化结果都会被丢弃。这个方案会改变初始对选择策略，应由算法开发者自行实现并对比注册率、点数和误差；本次没有替换该逻辑。

异常再次出现时，可立即在相同环境运行以下重放，记录当时是否使用调试器、是否有其他计算任务。脚本也记录当前 BLAS 线程数、墙钟/进程 CPU 时间，以及 Python trace 是否激活，便于下一次区分计算工作量、CPU 运行速度和等待时间。

```powershell
.venv/Scripts/python.exe scripts/profile_initialization.py `
  outputs/ui_20261017_093421_cb4035 `
  --repeat 2 --output reports/init-check.json
```

用 `--blas-threads 1` 做独立进程线程对照；用 `--profile` 输出 cProfile 的 `.prof` 和按累计耗时排序的 `.txt`。输入目录保持原样，报告必须输出到输入目录以外。
